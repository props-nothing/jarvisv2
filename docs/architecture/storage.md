# Storage Architecture

## Modes

### Local mode

- SQLite is canonical structured storage.
- Local application-data directories hold large artifacts.
- The OS keychain holds secret material; the database stores `SecretRef` identifiers.
- SQLite full-text search is available before semantic retrieval.

### Server mode

- PostgreSQL is canonical structured storage.
- pgvector indexes embeddings.
- Object storage holds large documents, media, exports, and optional recordings.
- A configured secret manager holds credentials.

The application uses domain repositories and unit-of-work ports. It does not pretend SQLite and PostgreSQL have identical SQL or operational behavior.

## Data Ownership

JARVIS stores canonical:

- users, clients/devices, workspaces, and grants
- sessions, messages, runs, steps, usage, and artifacts
- tool definitions/snapshots, calls, approvals, and decision receipts
- connector accounts, scopes, sync cursors, and webhook subscriptions
- memories, entities, relations, documents, and indexes
- events, inbox/outbox entries, workflows, schedules, jobs, and attempts
- notifications and voice calls
- runtime instances and opaque runtime bindings
- audit records and schema/config versions

External provider IDs are references, never primary identity by themselves.

## Transaction Boundaries

Use one database transaction to:

- validate expected state/version
- write the state transition
- write audit metadata
- enqueue an outbox event
- commit before dispatching asynchronous work

Never hold a database transaction open across a model call, network API, human approval, or long-running computation.

For an external effect:

1. Persist normalized intent and idempotency identity.
2. Commit.
3. Execute outside the transaction.
4. Persist provider evidence and normalized outcome.
5. Enqueue follow-up event in the same outcome transaction.

If step 3 completes but step 4 fails, mark/recover the attempt as `unknown` and reconcile; do not assume failure.

## Concurrency

- Use UUIDv7 identifiers generated by the application.
- Store timestamps in UTC with sufficient precision; retain user timezone separately for presentation/scheduling.
- Use optimistic version columns for interactive state machines.
- Use leases with owner, expiry, heartbeat, and fencing token for workers.
- Enforce uniqueness for idempotency keys, external event IDs, active singleton jobs, and provider bindings.
- Keep append-only attempt/audit records even when current-state rows are updated.

SQLite runs with one logical writer coordinator per profile. PostgreSQL supports multiple workers with row locking/skip-locked or advisory locks only where documented and tested.

## Migrations

- Number every migration monotonically and record application/schema compatibility.
- Test empty install and upgrade from every supported release boundary.
- Prefer expand/migrate/contract: add compatible structures, backfill, switch code, remove later.
- Do not perform destructive cleanup in the same release that stops reading the old shape.
- Back up local databases before risky migrations and verify the backup can open.
- Refuse to run against a newer unsupported schema; `doctor` explains recovery instead of guessing.
- Keep SQLite and PostgreSQL migrations behaviorally aligned but backend-native.

### Implemented SQLite baseline

`P1-006` uses embedded SQLx migrations under
`crates/jarvis-storage/migrations/sqlite`. Startup accepts only an empty database
or one carrying the JARVIS SQLite application ID, and cross-checks
`PRAGMA user_version`, `jarvis_storage_metadata`, and successful SQLx migration
history. A newer or inconsistent marker fails before normal operation.

Every connection explicitly enables foreign keys, recursive triggers, a bounded
busy timeout, `trusted_schema=OFF`, and `synchronous=FULL`. WAL is enabled only
with bundled SQLite 3.51.3 or newer, which includes the upstream WAL-reset
corruption fix. The data directory and database files retain the user-only path
policy defined in [OS application directories](../research/integrations/os-application-directories.md).

## Backup And Restore

Local backup uses SQLite's consistent backup mechanism, not a live file copy, plus an artifact manifest and checksums. Server backup coordinates PostgreSQL and object-storage retention. Secret material follows its provider's export policy and is never silently placed in a plaintext archive.

Before upgrading a recognized local schema, JARVIS creates a new compact
snapshot with `VACUUM INTO`. Migration begins only after that snapshot
independently passes `PRAGMA integrity_check`, `PRAGMA foreign_key_check`, and
application/schema identity checks. The verified file remains beside the source
database with both schema versions in its filename. Automated retention,
manifests, checksums, and user-facing restore are later backup tasks; until then,
recovery preserves the verified file and requires an explicit operator action.

Restore validation checks:

- archive format and checksums
- schema/app compatibility
- database integrity
- object references
- profile/workspace identity
- secret references without exposing values

Restore into staging or a new profile first where practical. Release gates include an actual restore drill.

## Search And Embeddings

Source text and metadata remain canonical. Full-text and vector data are rebuildable indexes.

Store embedding provider/model, dimensions, normalization, input hash, chunker version, and created time. Never compare vectors with incompatible metadata. Re-indexing is a durable, resumable job and does not block basic lexical memory use.

## Objects And Media

Large payloads use content-addressed or opaque object keys with metadata in the database. Enforce type, size, ownership, retention, and malware/content-processing policy before use. Never derive a filesystem path directly from a user or model filename.

## Secrets

Database rows contain:

```text
secret_ref_id
provider
scope/owner
purpose
created/rotated timestamps
health metadata without secret value
```

Resolution occurs only inside the adapter immediately before use. Redaction works on known secret values and structural patterns, while logs avoid secret-bearing URLs and headers by construction.

## Data Deletion

Deletion is a workflow with a manifest, not a single `DELETE` statement. It covers canonical rows, derived indexes, objects, caches, backups according to retention policy, runtime bindings, connector subscriptions, and documented provider-side data. Completion produces a user-visible receipt without reproducing deleted content.

The conceptual table model is in [schema.md](../data/schema.md).
