# ADR-0102: Two pushes routed on keys of opposite provenance

- **Status:** Accepted
- **Date:** 2026-10-01
- **Slice:** `P5-005` (the Google connector — routing a Calendar notification to the account whose channel it
  names). Completes the join `ADR-0100` and `ADR-0101` each left open.
- **Relates to:** `ADR-0097` (the Gmail router, whose `Ambiguous`/`Unknown` shape this mirrors and whose key is
  the **opposite** provenance), `ADR-0101` (the token verifier this feeds the stored value to), `ADR-0100` (the
  message whose `channel_id` this matches), `ADR-0098` (one address, one account — the same "a duplicate is
  unactionable and invisible" argument for a registration collision), and `ADR-0094`'s family: an unroutable
  delivery is acknowledged rather than refused.

## Context

A Calendar notification names the **channel** (`X-Goog-Channel-ID`) and **never the account** — the account is
whatever the `watch` call was authenticated as. So a delivery "a calendar changed" arrives with no way to know
**whose** calendar, and the sync it triggers needs one account's stored credential. That is exactly the gap
`ADR-0097` recorded for Gmail — *"a delivery names a mailbox, and nothing mapped it to an account"* — but for
the **other** Google mechanism, and `ADR-0100`/`ADR-0101` left it open in as many words: reading a message and
verifying its token does not say whose account to act on.

Attribution is a **join** against what the connector registered, and the two Google mechanisms join on values
of **opposite provenance**:

| | Gmail (Pub/Sub) | Calendar (channels) |
| --- | --- | --- |
| key a delivery names | `emailAddress` — **the provider's** value | `X-Goog-Channel-ID` — **the connector's own** value |
| what the connector stores | the address `getProfile` reported | the id **it chose** when it called `watch` |
| so a match is | a comparison against **untrusted text** | a **lookup in its own records** |

That difference is the finding, because it inverts the safety of the most natural optimisation. `ADR-0097`
makes routing **byte-exact** and reports a case-only near-match rather than acting on it, **because the address
is untrusted provider text** and Google publishes no canonicalisation rule. A channel id is the connector's own
generated value, so it has no case ambiguity to *report* — a case variant is simply a **different id**, and the
rule that covers both mechanisms is "compare the field as the provider sent it". Getting the direction wrong is
the failure mode in both cases: case-folding the address could read the wrong mailbox, and case-folding the id
could pick the wrong account; a prefix match makes both worse.

## Decision

1. **`route_channel(message, registrations) -> ChannelRoute` attributes a Calendar delivery to an account by
   its channel id**, mirroring [`route_delivery`](crate::google::routing::route_delivery)'s shape: three
   variants — `Exact(AccountReference)`, `Ambiguous { accounts }`, `Unknown` — where only `Exact` may be applied
   automatically and the two non-matches are **not** `None`. The id is matched **byte-exact**.

2. **The match is a lookup in the connector's own records, and the comparison says so.** Unlike `route_delivery`,
   the key here was **generated by this connector**, so a match is finding the registration it made rather than
   trusting a string the provider sent. The id is still *echoed* through an unauthenticated channel and so
   remains untrusted **input** — but it **selects** (an account to read with that account's own credential) and
   never **authorises**, which is `ADR-0097`'s rule unchanged. The token check is a **separate** control.

3. **A `ChannelRegistration` binds the channel id, the account, and the token, so a route cannot mispair them.**
   The argument is `&[ChannelRegistration]` rather than an `(id, account)` list, for the reason `route_delivery`
   takes `&[VerifiedAccount]`: separate lists would let a caller pair one account's reference with another's
   channel and route to the wrong mailbox with nothing able to notice. `token()` reaches the stored value (for
   [`verify_channel_token`](crate::google::channel::verify_channel_token)) without the field being public, and
   the hand-written `Debug` redacts it (`ADR-0091`).

4. **`token: None` is a recorded choice, not a missing value.** The guide makes the channel token optional, so a
   registration with no token is one the connector **chose** not to protect, and
   [`verify_channel_token`](crate::google::channel::verify_channel_token) reads it as
   [`ChannelTokenCheck::Absent`](crate::google::channel::ChannelTokenCheck::Absent) — **not** a refusal. An
   `Option<SecretValue>` with a sentinel would have made "I forgot the token" expressible as "there is none".

5. **Routing and verification answer different questions, and both must be run.** A delivery can route
   (`Exact`) yet **fail** verification (a mismatched or missing token), and a delivery for an **unregistered**
   channel routes `Unknown` and cannot be verified **at all**, because there is no stored value to compare
   against. So the natural sequence is route, then `verify_channel_token(registration.token(), message)` — and a
   test asserts routing **ignores** the token entirely, so the two controls are provably independent.

6. **A registration collision is `Ambiguous`, and the route carries a count rather than a pick.** Reachable only
   if a channel id is reused — the guide *recommends* a UUID "so it is unique", which is a recommendation, not an
   enforcement — and undecidable without a person: picking the first, oldest, or most recent registration would
   sync one account under another's identity. This is `ADR-0098`'s "one address, one account" argument applied to
   a channel: a duplicate makes the route unactionable and looks exactly like two legitimate channels.

## Consequences

- **The Calendar push path is now end-to-end on paper.** `ADR-0099` *named* the `EchoedChannelToken`
  authenticator, `ADR-0100` *read* the message it arrives on, `ADR-0101` *verified* its token, and this one
  *routes* the delivery to an account. Reading, verifying, and attributing are the three things a push handler
  must do before it can start a sync, and all three now exist as tested decisions.
- **The finding is the provenance inversion, and the general rule is that a key's origin decides how strictly it
  may be compared.** A **provider-supplied** key may only be compared as the provider sent it (byte-exact, no
  canonicalisation, near-matches **reported**); a **connector-generated** key may be compared against its own
  record (a lookup). The two mechanisms happen to want the same strictness for opposite reasons, which is worth
  recording because a reader who generalised from one would get the other wrong — `ADR-0097` reports a
  case-differs *state*, while a channel id has no such state to report, and treating one mechanism's rule as the
  other's would add either a spurious state or a dangerous fold.
- **Two guards were falsified A-B-A with compiling mutants.** (a) The exact-match comparison mutated to
  `starts_with` — a prefix match, the loosest plausible mistake — which routed a delivery naming
  `channel-alph` to `channel-alpha`'s account; the test failed with *"`channel-alph` is not a registered channel
  id"*. (b) The collision arm mutated so a count above one fell through to `Unknown` instead of `Ambiguous`,
  which would hide a genuine registration collision as "no such channel"; the test failed
  (`left: Unknown, right: Ambiguous { accounts: 2 }`). Both restored byte-identically.
- **A compile error caught a derive/impl clash before any test ran.** `ChannelRegistration` derived `Debug`
  **and** hand-wrote it (to redact the token), which is `E0119` — and it is worth naming because the *intent*
  was the redaction: the derive was the redundant half, so the fix was to drop the derive, not the hand-written
  impl. The compiler refused a type that would have silently printed the channel token.
- **⚠ A test-helper defect was fixed before it could pass for the wrong reason.** The first
  `message_for_channel` helper built the header list from a **non-`'static`** slice, which does not borrow-check
  against the fixture's `&'static [u8]` type — so the fix leaks the id (test-only) rather than widening the
  fixture types. Left unexamined it would have been a compile error, but the same helper shape is where the
  `ADR-0101` hardcoded-length trap came from: **the fixture layer is where a test stops testing the code.**
- **A limit remains: nothing calls `route_channel`, and nothing registers a channel.** There is no `watch`
  executor and no channel store, so — as with every slice of this mechanism — the route is a decision with tests
  rather than enforced behaviour. The registration set is a **slice passed in**, not a store, so a collision is
  only reachable if a caller hands in a duplicate; a store could enforce uniqueness, which is the revisit
  condition `ADR-0098` names for the account case.

## Alternatives considered

- **Match the channel id case-insensitively or by prefix.** Rejected — the prefix form is exactly the mutant the
  test kills. The id is an identifier the connector generated; a prefix match would route a delivery for
  `channel-alph` to `channel-alpha`'s account, and there is no canonicalisation reason to fold case, because the
  value is the connector's own and it can compare the bytes it stored.
- **Report a case-differs state, as `route_delivery` does.** Rejected: that state exists for Gmail because
  `emailAddress` is **untrusted provider text** with no published canonicalisation rule, so a near-match is
  genuine evidence about identity. A channel id has no such ambiguity — it is the connector's own value — so the
  state would be unreachable, and an unreachable variant is the "a variant nothing constructs" defect this phase
  keeps finding.
- **Take `&[(String, AccountReference)]` instead of `&[ChannelRegistration]`.** Rejected for the reason
  `route_delivery` takes `&[VerifiedAccount]`: separate lists let a caller pair a channel with the wrong
  account, and the type that binds them belongs in the signature.
- **Return `Option<AccountReference>`.** Rejected: three states, and `Ambiguous` (a registration collision) must
  not read as `Unknown` (a channel never registered) — only one is a defect in this connector, and the operator
  action differs.
- **Have `route_channel` also verify the token.** Rejected: routing (which account) and verification (is this
  really that channel) are separate controls with separate failure modes, and a delivery can route yet fail
  verification or be unroutable yet carry a well-formed token. Fusing them would make an unroutable delivery
  unverifiable by construction and hide which control failed.
- **Refuse an unroutable delivery so it is retried.** Rejected for the reason `ADR-0097` records: the
  registration set is a **local** fact, so a channel that matches nothing today matches nothing on the next
  delivery, and `ADR-0094` makes a negative acknowledgement subscription-global — refusing would slow every
  other channel for a message that can never become routable. Acknowledge and record.

## Conditions that would justify revisiting

- **A channel registration store exists** that enforces channel-id uniqueness, at which point `Ambiguous`
  becomes an invariant violation rather than a reachable state and the count can become an assertion — the same
  move `ADR-0098` names for the account case.
- **A `watch` executor / delivery endpoint is built**, which is where `route_channel` and
  `verify_channel_token` become *used* rather than *available*, and where the route-then-verify sequence is
  exercised against a received delivery rather than against values this crate builds.
- **Google changes the channel-id contract** (defines it as case-insensitive, or reuses ids across resources),
  at which point decision 1's byte-exact match and decision 6's collision handling are revisited against the new
  text.
- **The Gmail router and this one are unified.** They share the `Exact`/`Ambiguous`/`Unknown` shape and the
  "carry a count, not a pick" rule but differ in key provenance; if a third provider is added, a shared
  `DeliveryRoute` parameterised by key provenance would remove the duplication — and the provenance difference
  would have to survive the generalisation rather than be flattened by it.
