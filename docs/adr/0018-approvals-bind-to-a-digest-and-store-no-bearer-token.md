# ADR-0018: An approval is a decision record bound to a digest, with the nonce stored as a digest

**Status:** Accepted

**Date:** 2026-09-22

## Context

`P3-004` requires "durable approval requests, expiry, approve/deny/cancel, authenticated approvers, and
resume semantics". Three documents constrain it, and between them they decide the design.

`docs/architecture/security.md` calls an approval "a decision record, not a model message" and lists
its contents: approval ID and one-time decision nonce, canonical intent hash and preview, requesting
run/step/tool/version, actor/workspace/client and eligible approvers, effect/risk and policy version,
creation/expiry and decision timestamps, decision channel and authentication strength. It also lists
"Model self-approval/confused deputy" as a threat whose control is an "authenticated approval receipt
bound to exact intent, actor, policy version, expiry, and state version", and requires "approval
forgery, replay, expiry, mutation, and stale-state tests".

`docs/architecture/events-and-workflows.md` states the constraint that shapes storage: "Approval is
not a permanent bearer token", and "on approval, execution revalidates current identity, policy,
connector/account health, target state, and intent hash".

`docs/architecture/runtime-and-models.md` distinguishes the documented `cancelled/expired` edge from a
cancellation: "`awaiting_approval` is cancellable but not failable... an approval that times out is the
documented `cancelled/expired` edge."

Two decisions were needed, and both turned out to be about what must **not** be representable.

**First: where the nonce lives.** The requirement is a one-time decision nonce that defeats
self-approval, and the table is durable. If the nonce is stored, the row is a bearer token — a leaked
backup would let anyone approve anything. If it is not stored, no decision can be verified against
anything.

**Second: where the decision rules are enforced.** Four rules apply to a decision: the nonce, the
strength floor, the expiry, and the self-approval refusal. The store is the only place that holds the
nonce digest, and the domain is where the other rules belong.

## Decision

**1. The nonce is generated by the platform and stored only as a SHA-256 digest.** The presented value
is compared against the stored digest, and the stored digest is then rotated to the digest of the
empty string so it can never match again. A leaked row proves a decision happened without yielding the
ability to make one, which is what "not a permanent bearer token" requires in a durable record.

**2. A storage-loaded request cannot verify a nonce, and says so.** `ApprovalRequest` carries a
`nonce_usable` flag, `false` for a value rebuilt by `from_stored`. Calling `apply_decision` on such a
request returns `InvalidApprovalField::NonceUnavailable` rather than comparing the placeholder it
holds. The store performs the digest comparison and then calls
`ApprovalRequest::apply_verified_decision`, which enforces the remaining three rules.

This split was forced by a **failing test rather than by design**. The first implementation had
`from_stored` fabricate a `DecisionNonce` from the stored digest and let `apply_decision` compare it —
which meant the fabricated value was itself a presentable secret, so the digest's whole purpose was
defeated. Nineteen tests passed and one failed, and the failure was the security property.

**3. Expiry is evaluated in Rust, never in SQL.** `jarvis_core::UtcTimestamp`'s `Rfc3339` rendering
omits the fractional part when it is zero, so `"...00Z"` sorts **after** `"...00.5Z"` as text. A
predicate like `expires_at < ?1` would therefore treat an expired row as unexpired. Every comparison
uses `unix_nanos()`. The migration's comment says the same thing, and a core test pins the underlying
ordering defect so it cannot be rediscovered by accident.

**4. Expiry is a read-side fact, not a stored state.** An undecided row stays `pending` forever; its
*effective* state is `pending` or `expired` depending on the clock. Recording `expired` would require a
sweep job for correctness rather than for tidiness, and a row restored from a backup would be wrong. A
decided-and-approved row likewise stops authorizing at its expiry without its stored state changing.

**5. The intent is bound by a canonical digest, and the parts cannot bleed into each other.**
`CanonicalIntentHash` hashes the tool, its version, and a **sorted-key** JSON rendering of the
arguments, separated by `\u{1f}`. Without the separator, `("a", "bc")` and `("ab", "c")` would hash
identically, so one approval would authorize a different tool. Sorting is explicit rather than relying
on `serde_json`'s `BTreeMap` default, because that default is a property of a feature flag.

**6. One approval per intent per run, enforced by a unique index.** Two pending approvals for one
action would mean two prompts for one effect, and answering either would appear to authorize it. A
**changed** action hashes differently and is therefore a separate approval, which is required:
editing the action invalidates the approval.

**7. The requesting actor cannot approve its own request.** `security.md` names "model
self-approval / confused deputy" as the threat, and for a local single-owner profile the actor is the
user, so an equal identifier is either a bug or a forgery. Refusing is the fail-closed choice.

**8. A second decision is refused.** A denial cannot be overwritten by a later approval. Enforced
twice: the domain refuses an already-decided request, and the write is a guarded `UPDATE` requiring
`state = 'pending'`, so a decision that races loses rather than overwriting the winner.

## Consequences

- A leaked database row is inert. It reveals that a decision happened, who made it, and through which
  channel, and it cannot be used to make one.
- A forged decision is reported as `ApprovalNonceMismatch` rather than as a generic invalid request, so
  the caller learns which guard fired.
- A voice-originated risk-3 approval cannot be self-satisfied: the strength floor rejects a
  `ChannelEvidence` decision, which is `security.md`'s rule enforced rather than documented.
- The five test categories the security document requires each have a test named after them, so a
  missing category is visible rather than implied.
- The storage layer holds one security rule — the nonce digest comparison — and the domain holds the
  other three. That is a split of necessity (only the store has the digest), and it is recorded here
  rather than left as an accident of layering.
- Two defects were found by running the tests rather than by review, and both are now tests: the
  placeholder-nonce flaw above, and a `state`-versus-decision cross-check in the decoder that could
  never fail because `state` *is* which decision was made. The second is documented in the code as
  removed, so a future reader does not add it back.

## Alternatives considered

- **Store the nonce and forbid reading the column outside the repository.** Rejected: a durable row is
  exactly the thing that leaves the process — backups, exports, restored profiles — so "do not read it"
  is not a control.
- **Derive the nonce from the approval ID and a server secret.** Rejected: it makes the nonce
  recomputable by anyone who learns the secret, and it removes the one-time property, because the
  derived value stays valid until the secret rotates.
- **Keep the domain's single `apply_decision` and pass the stored digest into it.** Rejected as
  strictly worse: the function would have to accept "the real nonce or its digest", and a caller could
  pass the digest as if it were the nonce. The split makes the two paths different functions.
- **Re-implement the strength floor and expiry as SQL conditions.** Rejected: it would be a second copy
  of a security rule, and the SQL copy would be the one a reader trusts without seeing the domain tests.
- **Store `expired` as a state written by a sweep.** Rejected: it makes correctness depend on a job
  running, and a restored backup would carry a stale state.
- **Compare `expires_at` in SQL after padding the stored timestamps.** Rejected: it would require the
  padding everywhere and would not fix the existing `inspect.rs` ordering or the `recorded_at` index.
  The timestamp-format fix is a migration across every column and belongs in its own slice, not in this
  one.
- **Salt or key the intent hash.** Rejected: the intent is not a secret — the preview already states it
  — and the binding comes from recomputation, not from the digest being unforgeable alone. The research
  record records why a keyed construction is the wrong tool here.
- **Let an approval be decided only once but re-requestable for the same intent.** Rejected in favour of
  the unique index: a second prompt for an action already denied is how a denial gets worn down.
